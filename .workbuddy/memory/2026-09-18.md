## ARCH-2b 实时调用治理收口（已落地，提交在 P4-9a 之后）

### 问题（改造前）
- Python 侧 `ChatOpenAI` 没关 SDK 重试（默认 2 次）→ 「一次逻辑尝试」背后可能打了 3 个 HTTP 请求，
  观测耗时与上游计费对不上账，超时预算也被悄悄吃掉。
- 解析重试**每次重置完整超时** → 一操作最坏等待 = (重试次数+1) × 单次超时。
- Java 侧逐题评估虽已走 StructuredOutputInvoker，但没有预算：慢模型会一直等到 HTTP 超时；
  失败只有一句「模型不可用」，分不清超时 / 不合契约 / 上游报错。
- 输入无 backstop、结构化输出未封顶。

### 做法
- Python `LlmExecutor`：operation deadline（每次尝试只用剩余预算）、`llm_min_attempt_ms`
  剩余不足则不再发起（下限不超过预算一半，小预算不会被吃光）、`requests` 与实际请求一一对应、
  输入超限截断最后一条并留标记、结构化输出 `max_tokens` 封顶、`budget_exhausted` 区分
  「预算用尽」与「模型不合契约」；`metrics_snapshot` 增加 avgRequests / degradedRate。
- Python 构造点：`chat.py` 与 `studio.py` 均 `max_retries=0`（唯一重试责任层 = 执行器），
  新参数从 config 传入；`.env.example` 补注释。
- Java 新增 `StructuredCallPolicy`（realtime / background 两档）+ `StructuredOutputProperties`
  新键（`structured-background-budget-ms` / `structured-realtime-budget-ms|-max-attempts|-min-attempt-ms`）；
  `StructuredOutputInvoker` 增加带策略的重载：预算用「提交到虚拟线程 + orTimeout」实现
  （阻塞式调用无法打断，超时后只是不再等待；虚拟线程避免被放弃的调用占满池子），
  失败分类 TIMEOUT / PARSE_FAILED / UPSTREAM 进日志与指标 tag；逐题评估改用实时档。
- 后台档默认不限预算（异步任务允许慢，由 HTTP 超时兜底），保持既有行为。

### 验证
- Python：ruff / mypy / pytest 139 通过（新增 6 例：预算共享、剩余不足不再发起、截断、封顶、SDK 重试为 0 的断言）。
- Java：`:app:test` 全绿（新增 `StructuredOutputInvokerTest` 5 例）。
- 真实链路（8082，自起自停）：自适应会话提交真实作答 → 831ms 完成逐题评估并返回下一题，
  turnVersion 正常推进；探针会话已删除，库中无残留。

### 认知
- 小预算下「最小有意义尝试」的下限必须随预算缩放，否则 1 秒预算会被 1.5 秒下限直接吃掉、连一次重试都不允许
  （测试先暴露了这个问题）。
- 时间预算要靠「提交到虚拟线程 + 超时不再等待」实现；Spring AI 的阻塞调用无法真正取消，
  这是必须写进注释的取舍。

## P4-9a 逐轮请求幂等与会话推进一致性（已落地）

### 问题（改造前）
- 逐轮提交（submit / skip / complete）无请求标识、无会话版本；只校验「index 落在题库内」，
  不校验「是不是当前待答题」、也不看会话状态 → 重复 / 并发 / 晚到的提交各自独立推进一次。
- 一轮推进被拆成 3 个独立事务（答案 / 索引 / 状态），中间失败会留半状态。
- 模型调用虽在事务外，但推进本身不原子；评估触发无代次，重复投递会各自评一遍。

### 做法
- `V20260919__interview_turn_idempotency.sql`：`interview_sessions.turn_version`（推进版本）+
  `evaluate_epoch`（评估代次）+ 表 `interview_turn_requests`（`(session_id, request_id)` 唯一，
  存动作 / 载荷指纹 / 原结果 / 前后版本，FK ON DELETE CASCADE）。
- 条件更新闸门（`InterviewSessionRepository`）：`applyTurn` / `applyTurnRequestingEvaluation` / `applyFinish`
  都要求「版本 = 提交方版本 + 待答题 = 提交的那一题 + 会话仍在进行中」，影响 0 行即拒绝（`INTERVIEW_TURN_STALE`）。
- `InterviewPersistenceService.applyTurn(InterviewTurnCommit)` 是逐轮**唯一写入口**：
  条件更新 + 答案 upsert + 幂等记录同一短事务；模型调用留在其外。
- `InterviewSessionService.recordTurn` 三段式：幂等重放（返回原结果）→ Redis 占位拒绝处理中重复
  （`setIfAbsent`，新增到 RedisService）→ 校验（状态 / 版本 / 待答题，不匹配时按 DB 重建缓存）→ 单事务落库。
- 结束与跳过共用同一边界：`completeInterview(sessionId, requestId, expectedVersion)` 走 `ofFinish`。
- 评估触发：消息带 `evaluate_epoch`，消费端 `tryMarkProcessing` 改为原子领取
  （`claimEvaluation`：代次一致且未完成），代次落后直接丢弃；重试先置回 PENDING 再入队。
- 前端：提交 / 跳过 / 结束生成请求标识（重试复用同一标识）并回传 `turnVersion`；
  `request.ts` 新增 `ApiError` 保留业务码，过期类错误（3004/3010/3011/3013）触发回源同步 + 可见提示。
- 新增 `utils/interviewTurnSync.ts`（纯函数，可单测）+ `test:interview-turn-sync`（已接入 CI）。

### 验证
- Java：`./gradlew :app:test --no-daemon` 全绿。新增 `InterviewTurnConsistencyTest`（11 例，mock）
  与 `InterviewTurnConsistencyIntegrationTest`（4 例，**真跑本地 dev 库**）。
- 前端：`pnpm run build`、13 个 `test:*`、`pnpm run test:e2e`（11 例）全绿。
- 真实链路（自起 8082 实例，用完即停，未碰 8081）：首次提交 200 → 同标识重发返回**同一结果**且
  DB 只有 1 行答案 / 1 条幂等记录 / `turn_version=1`；同标识换载荷 3010；过期版本 3011；
  非当前题 3013；交卷（无 body 也接受）后 `turn_version=2`、`evaluate_status=PROCESSING`（原子领取生效）；
  交卷重放 200；结束后的晚到提交 3004 且会话仍是 COMPLETED。
- 探针数据已清理（删探针会话 → 级联清证据并重算画像，Java 画像回到 61/2 条）。

### 教训 / 新认知
- **集成测试抓到被 mock 掩盖的真实缺陷**：`InterviewTurnCommit.ofFinish` 曾把 `completing` 置 false，
  导致提前交卷按「普通作答」推进（写回 IN_PROGRESS + 移动索引）。提交命令里
  「要不要收束到评估」与「怎么推进」必须分开表达（completing vs action/finishing）。
- `questions_json` 解析失败会被 `restoreSessionFromDatabase` 吞成 404「会话不存在（3001）」，
  排查时先确认题库 JSON 能反序列化（手写最小 JSON 就踩了这个坑）。
- 新增 `interview/guide/support/LocalDatabaseGate`：DB 集成测试共用的可用性门控 + 连接解析，
  原有画像集成测试已改为引用它（`@EnabledIf("...LocalDatabaseGate#available")`）。

## P4Q-2 批 2a：覆盖与时间驱动的计划状态（已落地，未提交）

### 问题（改造前）
- 创建契约只有 questionCount（3-20 题）× RESUME_QUESTION_RATIO：真实意图被压扁成题数，
  回答好与差都问同样多；没有时长与覆盖概念。
- 时间只存在于前端一个墙钟计时——模型等待都被算成用户答题时间。
- 结束原因只有候选耗尽 / 用户结束两种。

### 做法
- 创建契约：`plannedDurationMinutes`（5-120，缺省 20）+ `requiredTopics`；
  `questionCount` 降级为兼容字段（按每主问题 4 分钟折算）。规模 = 时长/4（夹 3-12）。
- `InterviewPlan`（model）：计划值对象；**未声明必要覆盖时「覆盖完成」不作为收束条件**
  （否则主问题问完就掐掉追问深挖——默认口径踩过这个坑）。
- 迁移 V20260922：`planned_duration_minutes` / `required_topics_json` / `consumed_seconds` /
  `question_presented_at`。覆盖状态**不落库**（候选池 × 轨迹可推导，落快照只会漂移）。
- 时间记账：条件更新里 `consumed_seconds += 展示→提交墙钟 − 本轮模型评估耗时`，与推进同事务；
  预算随推进响应载荷带回（前端不必每轮再发 GET）。
- 收束边界（commitTurn）：必要覆盖完成 > 预算用尽 > 候选耗尽；前两者掐断未展示的下一题，
  当前题不越过刚答完的这道；`decidedAction` 与 `endReason` 一一对应。
- 预算调整：`POST /sessions/{id}/budget`（planned = 已用 + 声明剩余），DB + 缓存一起更，当轮生效。
- 前端顶栏：有计划显示「剩余 N 分钟」（本地递减、每轮权威值重起算）+ 调整入口；
  无计划的旧会话保留墙钟展示。

## P4Q-2 批 2b：覆盖 / 预算 / 合法候选进入逐轮上下文（已落地，未提交）

### 做法
- `TurnEvaluationRequest` 新增三字段：`coverageSummary` / `budgetSummary` / `legalCandidates`；
  全部由 Java 确定性推导（计划 × 候选池 × 实际轨迹），修复路径 `of()` 留空 → 提示词给占位。
- 覆盖摘要：必要覆盖逐项「已覆盖 / 本轮正在考察 / 未覆盖」；已问话题带轮次与未作答数；
  尚未问的话题。判据与 Java 收束硬边界共用同一 `InterviewQuestionDTO.matchesTopic`
  （话题匹配从 `InterviewSessionService.topicMatches` 抽到 DTO，行为逐字不变）——两处口径不会分叉。
- 预算：剩余时间 = 计划 − 已提交用时 − 当前题已展示墙钟（不预估本轮模型耗时，模型等待本就不扣，
  只会略保守）；追问预算 = 当前追问组剩余未问题数（与 AdaptiveInterviewPolicy 同口径，
  其他组预置追问策略到不了，不计入）。旧会话无计划时明确写「不按时间收束」。
- 合法候选：本组剩余追问 + 未问主问题，带 `[标识] 类型｜话题｜难度：题干`（题干截 60 字）；
  其他组追问不在列；上限 6 条，截断写「还有 N 条未列出」。
- prompt：user 加三个 section；system 要求 recommendedFocus 落在候选内、预算 0 / 时间紧时转向
  未覆盖话题、缺失上下文不得编造。变量表从 `Map.of` 改 `LinkedHashMap`（超过 10 组上限）。

### 认知
- 「覆盖状态不落库」的延伸：喂给模型的覆盖摘要也只能实时推导；若另存一份快照，
  它会在第一次「跳过/转场」后与轨迹漂移，且硬边界用的是轨迹——模型看到的世界就错了。
- 「合法候选」必须与策略同口径，否则模型建议的题 Java 选不到（P4Q-3b 会消费候选标识，
  现在把口径定死比事后对齐便宜）。

- `./gradlew :app:test --no-daemon` 全绿；`TurnEvaluationContextTest` 新增 15 例
  （覆盖状态随轨迹变化、预算变化改变摘要、占位渲染、合法候选边界），
  `InterviewSessionAdaptiveTest` 新增真实数据接线断言（计划 + 用时 + 必要覆盖）。
- 未做真实模型链路：本轮只改上下文构造，外部 API 行为不变；提示词质量/延迟属 P4-9b。
